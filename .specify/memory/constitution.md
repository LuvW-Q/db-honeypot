## 核心原则

### 一、文档与注释完备（中文优先，不可协商）

所有项目文档、代码注释、提交说明与评审记录 **必须（MUST）** 以中文为主；
技术专有名词可保留英文原词。文档与代码是**同等重要**的交付物，不是附属品。

- **数据库对象注释**：每张表、每个字段、每个视图、索引、触发器、存储过程/函数、
  约束与迁移脚本 **MUST** 配有中文说明。表注释必须说明业务含义与数据来源；
  字段注释必须说明含义、单位、取值范围与空值语义；DDL **MUST** 使用 `COMMENT`
  子句将注释落入数据库。
- **必备文档**：README（环境搭建与运行方式）、数据库设计说明书（含 ER 图、
  关系模式、完整性约束与索引设计理由）、迁移变更记录、运维与备份恢复说明。
- **ER 图同步**：ER 图 **MUST** 以可版本管理的源文件（如 Mermaid / PlantUML）
  维护，并与 DDL 保持同步；两者不一致时 **MUST** 先修正再合并。
- **代码注释**：注释解释"为什么"与边界条件，禁止逐行复述代码；公共接口
  **MUST** 有中文文档注释，覆盖参数、返回值与异常。
- **同提交更新**：文档与注释更新 **MUST** 与对应代码变更在同一次提交中完成，
  禁止事后补写。

**理由**：本项目交付物包含课程设计文档与答辩材料，数据库设计与文档本身就是
核心成果；注释缺失会使攻击数据语义与安全假设无法被审阅和复现。

### 二、数据库设计优先：Schema 即契约

数据库模式是系统的单一事实来源，代码 **MUST** 围绕已评审的 Schema 编写。

- **设计顺序**：需求分析 → 概念模型（ER 图）→ 关系模式 → 完整性约束 → DDL，
  **MUST** 按此顺序推进；在 ER 图与关系模式通过评审前，**不得**编写持久化代码。
- **范式要求**：关系模式 **MUST** 达到第三范式（3NF）。任何反规范化 **MUST**
  在文档中记录动机、性能收益与一致性保障措施。
- **完整性约束**：每张表 **MUST** 有主键；外键 **MUST** 在数据库层声明并启用；
  业务规则 **MUST** 优先用 `NOT NULL`、`UNIQUE`、`CHECK`、`DEFAULT`、`FOREIGN KEY`
  等约束表达，禁止只依赖应用层校验。
- **命名与类型**：表、列、索引、约束的命名 **MUST** 遵循文档中固定的统一规则，
  避免保留字；字段类型 **MUST** 选择满足业务的最小类型，并明确精度、字符集与
  时间戳时区语义；金额与计数类字段 **MUST** 使用精确类型。
- **索引设计**：索引 **MUST** 依据实际查询模式设计，并在设计文档中列出每条索引
  的理由；**禁止**无依据堆叠索引。
- **变更方式**：Schema 变更 **MUST** 通过版本化迁移脚本执行，**禁止**手工直改
  任何已纳入版本控制的数据库结构。

**理由**：关系设计、完整性与可演进性决定了系统的正确性与可维护性，是数据库
项目的核心价值所在。

### 三、安全设计与数据最小权限

本项目通过模拟 MySQL 协议采集攻击行为，**必须**假设一切来自外部连接的输入
都是恶意的。

- **账号分离与最小权限**：数据库账号 **MUST** 按职责分离（迁移、应用读写、
  分析只读、备份），遵循最小权限原则；应用与分析 **禁止** 使用超级用户或
  具有 DDL 权限的账号。
- **防注入**：所有 SQL **MUST** 使用参数化查询或预编译语句；**禁止** 拼接任何
  外部输入生成 SQL；显式设置查询超时与结果集上限。
- **敏感数据**：口令与凭据 **MUST** 加盐哈希或不可逆摘要存储，**禁止** 明文落库；
  敏感字段 **MUST** 加密或脱敏，日志、导出与展示数据 **MUST** 脱敏。
- **蜜罐数据隔离**：采集到的 SQL 语句、用户名、口令、客户端信息 **MUST** 视为
  不可信数据——只存储、不执行；任何重放或分析 **MUST** 在隔离环境中进行；
  采集库与分析/展示库 **MUST** 做逻辑或物理隔离，分析侧账号 **MUST** 只读。
- **审计留痕**：关键写操作 **MUST** 记录审计信息（时间、来源、操作类型、结果）；
  审计表 **MUST** 仅追加，业务账号 **禁止** 修改或删除审计记录。
- **备份安全**：备份与恢复 **MUST** 有明确策略并定期演练；备份文件 **MUST**
  加密并按最小权限管控。

**理由**：蜜罐系统天然面向攻击流量，数据库一旦被外部输入污染或被越权读取，
整个项目的分析结论与可信度都会失效，安全设计是本项目不可妥协的底线。

### 四、事务完整性与鲁棒性

数据一致性 **MUST** 由数据库机制保障，而不是靠调用方自觉。

- **显式事务**：涉及多表写入的操作 **MUST** 在显式事务中完成，并在设计文档中
  明确隔离级别；禁止依赖自动提交的隐式行为实现业务原子性。
- **原子与幂等**：事务失败 **MUST** 完整回滚，不得留下半成品数据；关键批量写入
  **MUST** 支持幂等或可安全重放。
- **并发处理**：竞态、死锁与锁等待超时 **MUST** 有重试或降级策略；重试 **MUST**
  幂等，并设置最大重试次数与退避。
- **输入防线**：所有外部输入 **MUST** 在入库前校验长度、类型、编码与规模上限；
  超大或畸形载荷 **MUST** 截断或拒绝并记录，防止存储与查询被拖垮。
- **资源边界**：查询 **MUST** 设置超时与资源上限；分析类查询 **MUST** 限制扫描
  范围，**禁止** 无界全表扫描与无 `LIMIT` 的大批量导出。
- **迁移安全**：迁移 **MUST** 可回滚或提供等价恢复方案，执行前 **MUST** 备份；
  破坏性变更（删列、改类型、拆表）**MUST** 附带数据迁移、校验与回滚步骤。
- **失败可观测**：错误 **MUST** 记录含上下文的日志，**禁止** 吞异常或静默失败。

**理由**：蜜罐写入与攻击分析查询具有高并发、数据不可控、体量不可预估的特点，
鲁棒性设计直接决定系统能否稳定采集并可信分析。

### 五、测试先行与可验证性

关键行为 **MUST** 有可执行的验证手段，且 **MUST** 针对真实数据库验证。

- **真实引擎集成测试**：涉及数据库的功能 **MUST** 有基于真实数据库引擎的集成
  测试，**禁止** 用 Mock 替代数据库行为验证（约束、事务、锁）。
- **测试覆盖**：测试 **MUST** 覆盖约束生效（唯一、外键、非空、检查）、事务回滚、
  并发冲突、迁移升级与回滚、备份恢复。
- **安全用例**：安全测试 **MUST** 包含 SQL 注入载荷、超长输入、非法编码与越权
  访问场景；蜜罐采集数据 **MUST** 验证"只存不执行"。
- **可重复**：数据夹具 **MUST** 版本化，测试库 **MUST** 可从迁移脚本与夹具重复
  初始化；每个需求 **MUST** 有对应的验收用例。
- **回归优先**：缺陷修复 **MUST** 先补回归测试使其失败，再修复使之通过。

**理由**：数据库缺陷往往在数据积累后才暴露，测试先行使关系约束、事务语义与
安全假设在早期即可被验证。

## 技术栈与工程约束

- 本项目为"基于 MySQL 协议模拟的数据库蜜罐与攻击行为分析系统"。后端语言、
  框架与持久化引擎 **MUST** 在 `/speckit-plan` 阶段确定并记录于 `plan.md`；
  未记录的技术选型 **不得** 直接引入。
- 数据库设计 **MUST** 以标准 SQL 为主体；使用方言特性 **MUST** 在设计文档中
  说明原因与可移植性影响。协议模拟层与持久化层 **MUST** 解耦，协议解析失败
  **不得** 影响持久化可用性。
- 所有 DDL、迁移脚本与种子数据 **MUST** 纳入版本控制；ER 图源文件 **MUST**
  与 DDL 一并提交。
- 敏感配置（连接串、口令、密钥）**MUST** 通过环境变量或配置模板注入，
  **禁止** 硬编码进代码仓库；仓库中 **MUST** 提供配置模板与说明。
- 依赖 **MUST** 锁定版本；引入新依赖前 **MUST** 评估维护状态、许可证与已知
  安全漏洞。
- 性能基线（采集写入吞吐、典型分析查询响应时间）**MUST** 在 `plan.md` 中
  定义，并可通过基准数据验证。
- 文档与注释默认使用中文；涉及外部/攻击者输入的处理逻辑 **MUST** 在注释中
  写明安全假设与边界。

## 开发工作流与质量门禁

- 开发流程 **MUST** 遵循 Spec Kit 阶段：
  `/speckit-specify` → `/speckit-clarify` → `/speckit-plan` → `/speckit-tasks`
  → `/speckit-implement`。设计变更 **MUST** 回到对应阶段更新产物，禁止跳过。
- 每项任务 **MUST** 在 `tasks.md` 中登记，并随进展更新状态；实现 **MUST** 与
  `spec.md`、`plan.md` 保持一致，任何偏离 **MUST** 记录理由。
- 合并前 **MUST** 通过以下门禁：
  1. ER 图、关系模式与 DDL 三者一致；
  2. 迁移脚本在空库与存量库上均可重复执行验证；
  3. 相关集成测试与安全用例全部通过；
  4. 文档与中文注释齐全；
  5. 无明文密钥、无拼接 SQL、无超级用户连接。
- 提交 **MUST** 小而聚焦，一次提交对应一个逻辑变更；提交信息 **MUST** 使用
  中文并说明动机（建议遵循 Conventional Commits 前缀）。
- **禁止** 在演示或生产库执行未评审的 DDL；演示环境 **MUST** 能从迁移脚本
  完整重建。

## 治理

- 本宪法是项目的最高约束，**MUST** 优先于个人习惯、模板默认值与其他实践
  文档。与本宪法冲突的实现 **MUST** 修正，或按修订程序变更宪法本身。
- 修订 **MUST** 以书面提案发起，说明动机、影响范围与迁移方案；通过后 **MUST**
  更新版本号与"最后修订"日期，并同步受影响的 `plan.md` 与任务。
- 版本遵循语义化版本：不兼容的治理或原则删除/重定义 → MAJOR；新增原则或
  实质性扩展 → MINOR；措辞澄清与非语义修订 → PATCH。
- 每次评审 **MUST** 核对宪法符合性；违反 MUST 原则的实现 **MUST** 阻断合并，
  例外 **MUST** 记录理由并获得明确批准。
- 复杂设计 **MUST** 在 `plan.md` 的复杂度跟踪中说明必要性；无法说明的复杂度
  **MUST** 简化或移除。
- 本宪法 **MUST** 在每个项目阶段结束时复核一次，确保与项目实际保持一致。
